# CRM operational metadata capture — SELECT only

This package contains queries, not instance results. Keep all real returned metadata private and outside Git, PRs, Actions artifacts and workflow inputs. No real database has been queried by the author of this package. The historical application and old row counts are not preflight inputs. Any runtime validation uses disposable synthetic fixtures only.

The canonical migration, lab renderer and aborting proposal are unchanged. Renderer source reviewed: commit `2464efdf028468c2ff8f8912e8f4213dcc3c0fbc`. Canonical payload SHA256 is `32173fdde2d456d6d9da8f46b54e38f4535b699b3ca36d921f93f444105fecc6`.

## Exact limitation

`direct_wrapper.py` has **no operational mode**. `validate_contract()` first requires `scope='synthetic-ci'`, then a `crm_acl_fixture_*` database, `postgres` as both identities, NOSUPERUSER, exact server version `170006`, read committed and no event triggers. It also requires the lab's raw catalog arrays and raw Supabase rows. Its `render()` repeats the disposable-database fence in SQL. A real capture cannot be made admissible by renaming fields, fabricating a scope/database name, removing guards or replacing raw fields with hashes.

Do **not** run its `capture_sql()` on a real target: that lab query serializes broad function sources/configuration and complete Supabase statements. This package intentionally uses a different schema, `crm-operational-evidence-v1`. It supplies evidence for a separately designed/reviewed operational envelope; it is not input accepted by the existing renderer. Hash commitments preserve comparisons without exporting arbitrary stored SQL, defaults, comments, labels or configurations. They do not review the behavior of unknown functions or defaults.

## How the parent should collect

Use the parent's authorized direct query tool. Send each file as one independent SQL call; do not assume multi-statement support, shared sessions, an outer transaction, autocommit, automatic ledger registration, output limits or a particular error/retry behavior.

1. Run `01_discovery.sql`. Check object existence, actual server version, declared column types, SELECT permissions and role capabilities. These queries target PostgreSQL 17 catalogs. A different major version, missing object, unexpected/custom type, denied permission, hidden field or truncated result is a blocker to that capture; report it without grants, guessed metadata or fallbacks. Observe BYPASSRLS freshly; do not assume it from history.
2. Run `02_scoped_catalog.sql`. It captures the three named relations, helper overloads and all their trigger links, associated indexes/TOAST/owned sequences, scoped dependencies, owners/ACLs/membership paths, and every event trigger/function. It never selects customer rows. Potentially sensitive metadata values are hashed. An unhashable missing-value representation is explicitly reported and remains unsupported; do not accept a partial contract. Review all owners, constraints, default dependencies, custom opclasses/types and unknown functions before designing any executable envelope.
3. Before preparing any history SELECT, independently verify both ledger relations are the same observed ordinary heap tables, with no RLS/forced RLS, rules, inheritance or partitioning, and builtin columns/access methods/index behavior. Stop on a view, foreign table, custom IO/access method, unknown policy or identity drift: a WHERE/CASE shape condition is not a sandbox for untrusted view/planner/policy behavior. Run `03_drizzle_history.sql` only after this and the exact three builtin Drizzle columns have been verified. It returns every ordered row, decimal integers as strings, valid migration hashes and a row hash. An anomalous hash value is redacted and flagged. Neither a historical row nor a proposed next ID is a baseline. No ID is reserved or supplied by these queries.
4. Run `04_supabase_manifest.sql`, then `05_supabase_page.sql` starting at its literal offset `0`. For the next page, replace **only** that offset with the returned `next_offset`. The page size is a collection parameter, not a claim about the transport's capacity; reduce it consistently if the parent verifies a smaller limit. Obtain every page until `has_more=false`. Each page repeats the full row count/digest. Require equal manifests and exactly one entry for each `row_number`; then rerun `04` and require the same manifest. Any truncation, error, count mismatch, duplicate/null version or digest change blocks completeness. Do not fill gaps from memory. Non-numeric version text is redacted and represented by a hash.
5. From the **fresh** discovery result, use its `sequence.state_select` verbatim, only after SELECT capability and sequence identity are confirmed. That generated SELECT quotes the observed identifiers and pins the observed relation/database identities. It returns explicit `last_value` and `is_called`; no `nextval`, `setval`, lock, DDL or registration occurs. Missing permission is a blocker, not a reason to grant access or infer sequence state. Do not substitute `pg_sequences.last_value`: NULL there does not supply `is_called` or prove an unused sequence.
6. Run `06_activity.sql`. It returns current-database session/transaction/lock metadata, prepared-transaction identities with hashed GIDs, and logical-subscription metadata without connection settings. No query text, application names, addresses, credentials or GID text are returned. Restricted statistics visibility is UNKNOWN, not evidence of zero writers. Do not terminate, cancel, commit or roll back anyone's transaction.

Every result has its own timestamp, database identity, backend PID and snapshot marker. Compare repeated identity/metadata/ledger observations; do not silently rebind a recreated object. Multiple calls and sequence/statistics reads are **not** one coherent transaction snapshot. Matching before/after hashes do not exclude transient changes or ABA races. Initial capture is preparation only; it must be refreshed and independently reviewed within a newly coordinated window before any future admitted application.

Object/database OIDs are identities only within the externally verified target connection, not a cluster or endpoint identity proof. Row serialization can depend on session formatting settings; these are captured for comparison. No SET is issued to normalize a connection. The missing-value fingerprint uses binary array output only for an explicit builtin-type whitelist; unsupported IO is never invoked to make a fingerprint complete.

## Gates these SELECTs cannot satisfy

- They do not prove transport session continuity, timeout setup in the execution session, autocommit/COMMIT, automatic migration registration, atomic error handling, lost-response behavior or safe retry semantics. The parent must verify the actual transport separately.
- They cannot enumerate future external queues, CI jobs, Lovable appliers, pre-read migration clients or noncooperating owner DDL/ACL writers. The result explicitly leaves external coordination UNKNOWN. An empty activity/prepared list is not a DDL/ACL window.
- They do not authorize a real application or reuse an earlier window. F2 concurrent ACL normalization remains a limit. Keep the future window through independent postchecks and uncertain-response reconciliation.
- A different ledger/default/sequence convention, active event triggers, custom IO/operator behavior, unsupported metadata or different server version requires new design, isolated tests and independent review. Do not weaken the lab renderer to accept it.

`evidence.schema.json` describes the returned projections. No file contains a private object identity, history preimage, transport assertion or operational authorization.
